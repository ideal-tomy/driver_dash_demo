# 配車デモ LP 文言変更指示・日本語改善ナレッジ

対象: `driver_dash_demo` の `/lp`  
目的:
1. 現在のLP文言を、営業担当者が自然に説明する日本語へ変更する  
2. AI実装時に「変更前 → 変更後」で迷わず置換できるようにする  
3. 今後のLP・デモ文言改善に使える「日本語修正ナレッジ」として変更理由を残す  

---

# 0. 実装時の基本方針

この変更では、ページ構成・デモの意味・業務フローは変更しない。

変更対象は主に文言。

特に次のような表現は避ける。

- 主語や目的語を省きすぎた短文
- 「画面が決める」「荷物が出る」など、システムや画面を人のように扱う表現
- 短く見せるために意味を削った見出し
- 読み手が状況を頭の中で補わないと理解できない文章
- キャッチコピー化しすぎた説明文
- 「しません。」「変えません。」「なくしません。」のような短文の連続
- 実際の営業担当者が口頭では使わない表現

今回の優先順位は以下。

1. 一読で状況が分かる
2. 誰が何をするのか分かる
3. 業務の流れが自然につながる
4. 営業担当者が口頭説明しても不自然ではない
5. そのうえで簡潔にする

「短いこと」より「意味がすぐ分かること」を優先する。

# 2. セクション1: ヒーロー

## ラベル

### 変更前

`さっきの画面について`

### 変更後

`さっきの画面について`

変更なし。

## 見出し

### 変更前

`さっきの画面で起きたことは、これです。`

### 変更後

`帰り便に載せられそうな荷物を、担当者に知らせます。`

### 変更理由

変更前は「これです」と言っているだけで、何が起きたのか分からない。

変更後は、デモで何をしている画面なのかを最初の一文で説明する。

## 本文1

### 変更前

`空で戻る車に、隣の担当が持っている荷物が出てきました。`

### 変更後

`荷物を降ろして空車になった車両に、別の担当者が受けている荷物を載せられそうな場合があります。`

### 変更理由

「荷物が出てきました」は、何が起きたのか意味を補わないと理解できない。

また「隣の担当」は位置関係のようにも読める。

変更後は、車両が空車になったこと、別担当の配送依頼があること、その荷物を載せられる可能性があることを順番に説明する。

## 本文2

### 変更前

`載せるか載せないかは、画面が決めません。人が決めます。`

### 変更後

`その荷物を候補として画面に表示し、実際に載せるかどうかは担当者が判断します。`

### 変更理由

「画面が決める」は擬人化表現であり、営業説明として不自然。

「人が決めます」も誰なのか曖昧。

変更後は、システムは候補を表示し、担当者が最終判断する、という役割分担を明確にする。

## ボタン

### 変更前

- `もう一度画面を見る`
- `下の説明を読む`

### 変更後

- `もう一度画面を見る`
- `仕組みを見る`

### 変更理由

「下の説明を読む」はUI操作そのものを説明していて、内容を表していない。

「仕組みを見る」の方が、次のセクションで何を理解できるかが分かる。

# 3. セクション2: いま、現場で起きていること

## 見出し

### 変更前

`荷物の依頼は、担当ごとに分かれています。`

### 変更後

`担当が違うと、使えそうな車両や荷物の情報が見えません。`

### 変更理由

変更前は「依頼が分かれている」という事実しか説明しておらず、何が問題なのか分かりにくい。

変更後は、担当ごとに情報が分かれていることで起きる問題まで一文で伝える。

## 本文

### 変更前

- `ネット、FAX、電話。受けた人の手元にしかありません。`
- `空で戻る車があっても、隣の担当の荷物には気づけません。`
- `気づけないので、車は空のまま戻り、荷物は残ります。`

### 変更後

- `配送の依頼は、Web・FAX・電話などから入ります。`
- `受け付けた依頼は、それぞれの担当者が管理しています。`
- `そのため、荷物を降ろして空車になった車両があっても、別の担当者が持っている配送依頼には気づきにくくなります。`
- `結果として、車両が空車のまま戻る一方で、運べる可能性のあった荷物が残ることがあります。`

### 変更理由

変更前は短文を並べすぎていて、状況の因果関係を読み手が補う必要がある。

変更後は、依頼が複数経路から入る → 担当ごとに管理される → 別担当の情報に気づきにくい → 空車と荷物を組み合わせられない、という順番で説明する。

## 補足

### 変更前

`人数と件数は仮です。担当5人、1日20件として描いています。`

### 変更後

`人数と件数は説明用の仮設定です。デモでは担当者5人、1日20件として描いています。`

# 5. セクション3: さっきの画面で変わったこと

## 見出し

### 変更前

`担当の分け方はそのままです。見る場所だけ一つになります。`

### 変更後

`担当の分け方は変えず、依頼と車両の情報を一つの画面で確認できるようにします。`

## 本文

### 変更前

- `依頼は入った時点で、一つの表に並びます。`
- `担当は今まで通り分かれています。会議も組織も変えません。`
- `空になった車に、隣の荷物が候補として出ます。`
- `載せる・載せないは担当が押します。休息の確認と、FAXの読み取り漏れは消しません。`

### 変更後

- `Web・FAX・電話で受けた依頼を、一つの一覧で確認できるようにします。`
- `地域ごとの担当分けや、これまでの仕事の進め方を大きく変える必要はありません。`
- `車両が空車になったときは、近くに運べそうな荷物があれば候補として表示します。`
- `実際にその荷物を載せるかどうかは、これまで通り担当者が確認して判断します。`

## 接続文

### 変更前

`デモで押した「載せる／載せない」が、この候補です。`

### 変更後

`デモで選んだ「載せる／載せない」は、この候補に対する担当者の判断です。`

## 変わらないこと

### 変更前

- 誰がどの地域を持つか
- 載せるかの最終判断
- 休息とFAXの確認

### 変更後

- 地域ごとの担当
- 最終的な配車判断
- 休息時間やFAX内容の確認

## 変わること

### 変更前

- 同じ表を見る
- 空車の隣に候補が出る
- 確認は画面に残して人が見る

### 変更後

- 依頼情報を一つの画面で確認できる
- 空車と組み合わせられそうな荷物を確認できる
- 確認が必要な項目を画面に残せる

### 実装注意

もし現在の実装で「誰が確認したか」まで保存している場合は、最後の文言を `誰がどの候補を確認したか記録できる` としてもよい。実装事実に合わせること。

# 12. 日本語改善ナレッジ

ここから下は、今回のLPだけでなく今後のLP・デモ制作でも再利用する。

## ナレッジ01: システムや画面を擬人化しない

### NG

`載せるか載せないかは、画面が決めません。人が決めます。`

### OK

`候補として画面に表示し、実際に載せるかどうかは担当者が判断します。`

### 理由

画面は「判断する主体」ではない。

システムがすること、人がすることを具体的な動詞で分ける。

### 適用例

- 画面が決める → システムが候補を表示する
- AIが判断する → AIが候補を抽出し、担当者が確認する
- 画面が教える → 画面に表示する
- システムが気づく → 条件に一致する項目を検出する

## ナレッジ02: 「出る」を多用しない

### NG

`空車に、隣の荷物が出る`

### OK

`帰り便に載せられそうな荷物があれば、候補として表示します。`

### 理由

「出る」は意味範囲が広すぎる。

何が、どこに、どのような状態で表示されるのかを書く。

## ナレッジ03: 短文化のために主語・目的語を削らない

### NG

`決めるのは担当`

### OK

`実際に配車するかどうかは担当者が判断します。`

### 理由

短いキャッチコピーにしようとして意味が削られている。

業務説明では、誰が何を判断するのかを残す。

## ナレッジ04: 読み手に因果関係を補わせない

### NG

`ネット、FAX、電話。受けた人の手元にしかありません。`

`気づけないので、車は空のまま戻り、荷物は残ります。`

### OK

`配送の依頼は、Web・FAX・電話などから入ります。受け付けた依頼は、それぞれの担当者が管理しています。`

`そのため、別の担当者が持っている配送依頼には気づきにくくなります。`

### 理由

文章を短く分けすぎると、何と何がつながっているのかを読み手が推測する必要がある。

## ナレッジ05: 図の位置関係に依存した文章を避ける

### NG

`すぐ下の担当に戻る向きの荷物が入ります。`

`隣の担当の荷物`

### OK

`その近くでは、別の担当者が配送依頼を受けています。`

`空車になった車両で運べそうな荷物`

### 理由

「上」「下」「隣」は図を見ないと意味が分からない。

LP本文として読んでも意味が通る文章にする。

## ナレッジ06: 一つの説明の途中で別の論点を増やさない

### NG

`空で走った距離も、運べなかった荷物も、誰も数えていません。`

### OK

`担当者ごとに情報が分かれているため、組み合わせられる車両と荷物を見つけにくい状態です。`

### 理由

そのセクションが「情報分断」を説明しているなら、突然「計測不足」の問題を追加しない。

一つのセクションでは一つの論点を説明する。

## ナレッジ07: FAQで短い否定文を連発しない

### NG

- しません。
- 変えません。
- なくしません。
- 任せません。
- 違います。

### OK

質問の意図を受けて、普通の説明文として答える。

例:

`いいえ。条件に合いそうな組み合わせを候補として表示します。実際に配車するかどうかは担当者が判断します。`

## ナレッジ08: 「営業担当者が口頭で言うか」を確認する

文章完成後、以下を確認する。

- 顧客の隣で画面を見ながら、そのまま口に出して説明できるか
- 一度読めば意味が分かるか
- 言い換えないと説明できない文章になっていないか
- 「何のこと？」と聞き返される名詞がないか
- 主語・目的語を省きすぎていないか

営業担当者が口頭で言い直す必要がある文章は、LPでも書き直す。

## ナレッジ09: 「短いこと」を最優先にしない

### NG

`空車の隣に候補が出る`

### OK

`帰り便に載せられそうな荷物があれば、候補として表示します。`

### 判断基準

短文でも意味が明確なら短くしてよい。

意味が失われる場合は、多少長くても具体的な文章を使う。

## ナレッジ10: 見出しも説明文として成立させる

見出しだからといって、必ずコピーライティングをする必要はない。

業務デモでは、`一つの一覧を共有すれば、自分で必要な情報を確認できます。` のように、見出しだけで意味が通る形を優先する。

# 13. 今後のAI修正文作成フロー

## STEP 1: 元の事実を抽出する

例:

- 配送依頼はWeb・FAX・電話で入る
- 担当者ごとに依頼を管理している
- 車両が配送先で空車になる
- 別担当に運べそうな荷物がある
- システムは候補を表示する
- 最終判断は担当者が行う

この段階ではコピーを書かない。

## STEP 2: そのセクションで伝えることを1つ決める

例:

`担当者ごとに情報が分かれているため、空車と荷物の組み合わせに気づきにくい。`

## STEP 3: 営業担当者が口頭で説明する文章にする

キャッチコピー化しない。

専門家らしく見せる言葉を追加しない。

## STEP 4: 今回のNG/OKナレッジと照合する

特に以下を確認する。

- 擬人化していないか
- 「出る」を曖昧に使っていないか
- 主語・目的語を削りすぎていないか
- 図の位置関係に依存していないか
- 別の論点を追加していないか
- 短くするために意味を壊していないか

## STEP 5: 変更前 → 変更後 → 理由を保存する

新しい修正で良い事例ができた場合は、このファイルへ追加する。

推奨形式:

```md
## 変更例

### 変更前
...

### 変更後
...

### 変更理由
...
```

# 14. 今回の変更で確定させたい基本原則

1. キャッチコピーより、意味が通る文章
2. 短さより、一読で理解できること
3. 抽象語より、実際に起きていること
4. 「AI・システム」より、担当者の仕事の流れ
5. 擬人化より、具体的な処理
6. セクションごとに論点を1つにする
7. 既存業務を否定しない
8. 自動化を過剰に見せない
9. 最終判断を人が行う場合は明示する
10. 営業担当者がそのまま読める日本語にする

# 16. ナレッジ追加ルール

今後、このファイルへ事例を追加する場合は、単に「自然な日本語にする」というルールを増やさない。

必ず実例で残す。

推奨形式:

```yaml
category: human_decision
context: システムが候補を表示し、人が最終判断する場面

before: |
  載せるか載せないかは、画面が決めません。
  人が決めます。

after: |
  候補として画面に表示し、
  実際に載せるかどうかは担当者が判断します。

reason: |
  画面を判断主体として擬人化していた。
  システムの役割と担当者の役割を分けた。
```

「ルールだけ」ではなく、

- context
- before
- after
- reason

の4点を残す。

これを今後の日本語改善ナレッジの基本単位とする。
